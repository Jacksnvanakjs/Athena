# 小公司财报催化剂监控 — 设计文档

> **用途**：在 Athena 网站落地「AI 相关中小市值公司财报日历 → 评分 → 网站展示 → 财报前 2 天手机推送」。  
> **版本**：v1.1（2026-08-29）  
> **关联文档**：  
> - [小公司财报催化剂评分规则.md](./小公司财报催化剂评分规则.md)（评分/淘汰逻辑，本模块直接复用）  
> - [AI合作快讯监控-设计文档.md](./AI合作快讯监控-设计文档.md)（T0/T1/T2、推送通道、页面风格）  
> - [黄仁勋A档产业动作监控-设计文档.md](./黄仁勋A档产业动作监控-设计文档.md)（买卖窗口字段风格可对齐）  
> **原则**：早发现只上网站；**手机推送仅在财报发布前 2 个自然日**；同日多家 **合并一条推送**；网站与推送 **必须附带买卖窗口**。  
> **默认交易策略**：`POST_ER_BUY_WITHIN_2D` — **财报发布后尽早买，最大受益持有期约 2 个交易日内卖出**（校准自 2026-08 OKTA/CRWD/CRM）。

---

## 0. 给开发者的核心约束

1. **监控可很早**：一旦抓到候选池内公司的下次财报日，立刻入库并在网站展示。
2. **手机推送不能早**：**仅当 `earnings_date - today == 2`（自然日）** 时才允许 PushPlus / Server酱。
3. **同日多家合并推送**：同一推送日、多家满足条件 → **一条通知**，正文列表列出全部标的。
4. **远日不推手机**：`days_to_earnings > 2` 只写库、只上网站；`days_to_earnings < 2` 且尚未推过的，按补推规则（见 §3.2）。
5. **评分门槛**：网站可展示全部候选；手机推送默认仅 **综合得分 ≥ 75**（可配置）。
6. **买卖窗口必填**：每条 `EarningsEvent` 必须计算并展示 `strategy` / `buy_window` / `sell_window` / `sell_deadline`；**网站表格与手机推送均须展示**（见 §3A）。
7. **不做自动下单**；页面与推送必须含免责声明。
8. v1 **仅美股**；时区以 **美东 `America/New_York`** 判定财报日与「前 2 天」。

## 1. 项目目标

### 1.1 要解决什么问题

相对 NVDA / 未上市巨头，中等及以下市值 AI 链公司（如 OKTA、CRWD、LITE、SMCI）在 **财报 beat + 上调指引** 后，盘后～次日常出现 **+15%～+30%** 级波动（例：2026-08-26 OKTA/CRWD/CRM）。

系统目标：

1. **持续拉取** 白名单赛道内 T1/T2 公司的下次财报日期（可提前数周）
2. **按评分规则** 打分、淘汰，区分「仅展示」与「可推送」
3. **网站表格** 长期可见，方便人工浏览日历；每行附带 **建议买入/卖出时间**
4. **财报前 2 天** 才发手机提醒，避免过早噪音；同日合并推送；推送正文附带 **买卖窗口**
5. 默认策略对齐 OKTA/CRWD/CRM 实证：**暴涨从财报发布后启动，最大受益约在发布后 2 个交易日内**

### 1.2 不做什么（v1）

- 不自动交易、不给仓位建议
- 不保证 beat 必涨（评分只提高胜率，不承诺收益）
- 不监控市值 > $500B 的 T0（NVDA、MSFT、GOOG、AMZN、META、AAPL、TSLA、ORCL 等）
- 不做盘后「已发布财报」的实时解析推送（v1 只做 **发布前提醒**；盘后复盘可后续版本）
- 不把「合作快讯」与「财报提醒」混成同一条 push（频道/标题前缀分开）
- **不建议财报前埋伏博暴涨**（三家案例显示主升浪在发布之后）

### 1.3 与「合作快讯」页面的关系

落地在现有 **「AI 产业链合作快讯」**（`/deals`）页面内，增加 **「财报日历」Tab / 区块**，而不是另开孤立站点：

| Tab / 区块 | 数据来源 | 手机推送 |
|------------|----------|----------|
| AI 合作 | `deal_monitor` | 事件驱动，即时 |
| 黄仁勋动向 | `nvda_signal` | 事件驱动，即时 |
| **小公司财报**（本模块） | `earnings_monitor` | **仅 T-2 日** |

## 3. 「提前 2 天」推送规则（最重要）

### 3.1 时间定义

| 符号 | 含义 |
|------|------|
| `earnings_date` | 财报 **日历日**（美东日期，不含时分） |
| `session` | `AMC`（盘后）/ `BMO`（盘前）/ `TBD` |
| `today_et` | 当前美东日期 |
| `days_to` | `earnings_date - today_et`（整数自然日） |

### 3.2 推送资格矩阵

| `days_to` | 网站展示 | 手机推送 |
|-----------|----------|----------|
| `> 2` | ✅ 表格可见 | ❌ **禁止**（即使得分 90+） |
| `== 2` | ✅ | ✅ **主推窗口**（当日调度任务触发） |
| `== 1` | ✅ | ⚠️ **补推**：若 T-2 因故障未推成功，允许补推一次 |
| `== 0`（财报日当天） | ✅ 标「今日财报」 | ⚠️ 可选补推（默认 **关闭**，避免盘中噪音） |
| `< 0`（已过） | 移入「已发布」归档或隐藏 | ❌ |

**默认配置（写入 `config.py`）**：

```python
EARNINGS_PUSH_DAYS_BEFORE = 2          # 主推：前 2 天
EARNINGS_PUSH_ALLOW_T_MINUS_1 = True   # T-1 补推
EARNINGS_PUSH_ALLOW_T_DAY = False      # 财报日当天不推
EARNINGS_PUSH_MIN_SCORE = 75           # 手机推送最低分
EARNINGS_WEB_MIN_SCORE = 0             # 网站可展示全部入库候选（或设 60）
EARNINGS_LOOKAHEAD_DAYS = 90           # 日历抓取前瞻窗口（网站用）
EARNINGS_SCORE_LOOKAHEAD_DAYS = 14     # 深度评分只做近 14 交易日（省 API）
EARNINGS_STRATEGY = "POST_ER_BUY_WITHIN_2D"
EARNINGS_HOLD_TRADING_DAYS_MAX = 2     # 最大受益持有：约 2 个交易日
EARNINGS_CHASE_GAP_PCT_BLOCK = 15      # 跳空过大不追
```

### 3.3 同日合并推送（必须）

同一调度周期内，所有满足「今日应推」的标的：

1. 按 `earnings_date`（美东）分组
2. **每个 `earnings_date` 只发 1 条** PushPlus/Server酱
3. 标题示例：`【小公司财报 T-2】08-26 共 3 家：OKTA / CRWD / CRM`
4. 正文按得分降序列出每家：ticker、得分、盘前/盘后、一句话理由、关键风险

**禁止**：同日 3 家发 3 条手机通知。

### 3.4 去重

| 键 | 规则 |
|----|------|
| `push_dedupe_key` | `{earnings_date}_{sorted_tickers_joined}` 或按日批次 `batch:{earnings_date}` |
| 同一 `earnings_date` 批次 | **终身只成功推送 1 次**（补推除外：仅当 `push_channel` 为 failed/unconfigured） |
| 财报日改期 | 旧批次作废；新 `earnings_date` 重新走 T-2 逻辑；网站更新日期 |

正文第 4 点补充：每家必须带 **买入窗口 / 卖出首选 / 卖出最晚（2 交易日内）**（由 §3A 计算）。

## 3A. 买卖窗口策略（默认：财报后买，2 个交易日内卖）

> **策略代码**：`POST_ER_BUY_WITHIN_2D`  
> **校准样本**：2026-08-26 盘后 OKTA / CRWD / CRM 同日财报 → 盘后跳涨 → 08-27 正规盘把周涨幅做大（约 +19%～+28%）。  
> **结论**：最大受益窗口在 **财报数字落地之后起算的约 1～2 个交易日**，不是财报前。

### 3A.1 时间线（AMC 盘后为例，与三家一致）

```
T-2  手机推送提醒（准备，不买入博消息）
T0   美东 earnings_date 盘后发布
T0   盘后尽早买入（首选）          ← buy_window 起点
T+1  次日正规盘（主升浪常在此日）
T+1  收盘卖出（首选卖点）          ← sell_window 首选
T+2  收盘前必须清仓（最晚）        ← sell_deadline（2 个交易日内）
```

### 3A.2 按 session 计算买卖窗口

| session | 买入窗口 `buy_window`（尽早） | 首选卖出 `sell_window` | 最晚卖出 `sell_deadline` |
|---------|------------------------------|------------------------|---------------------------|
| **AMC**（盘后） | ① `earnings_date` **当日盘后**；或 ② 次日 **盘前**；或 ③ 次日 **09:35–10:00 ET** | **次日（T+1）16:00 ET 收盘** | **T+2 收盘**（发布后第 2 个交易日结束前清仓） |
| **BMO**（盘前） | ① `earnings_date` **当日盘前**；或 ② 当日 **09:35–10:00 ET** | **当日（T0）收盘** 或 **T+1 收盘** | **T+1 收盘**（仍落在约 2 个交易日窗口内） |
| **TBD** | 按 AMC 保守展示，并标注「时段待确认」 | 同 AMC | 同 AMC |

**人类可读示例（AMC，earnings_date=2026-08-26）**：

```
策略：POST_ER_BUY_WITHIN_2D（财报后买，2交易日内卖）
买入：08-26 盘后｜08-27 盘前｜08-27 09:35-10:00 ET（取能成交的最早）
卖出首选：08-27 16:00 ET 收盘
卖出最晚：08-28 16:00 ET 收盘前清仓
注意：财报前不建议重仓埋伏；跳空过大（相对前日收盘 ≥15%）不追
```

### 3A.3 字段（入库 + API + 推送共用）

| 字段 | 类型 | 说明 |
|------|------|------|
| `strategy` | str | 固定默认 `POST_ER_BUY_WITHIN_2D` |
| `buy_window` | text | 人类可读买入窗口（可含多段，用 `｜` 分隔） |
| `sell_window` | text | 首选卖出时点 |
| `sell_deadline` | text | 最晚卖出时点（**2 个交易日内**硬截止） |
| `buy_window_json` | JSON/text | 机器可读，便于前端高亮 |
| `hold_trading_days_max` | int | 默认 **2** |

`buy_window_json` 示例（AMC）：

```json
{
  "strategy": "POST_ER_BUY_WITHIN_2D",
  "session": "AMC",
  "buy_windows": ["earnings_day_after_hours", "next_pre_market", "next_open_0935_1000"],
  "sell_preferred": "t_plus_1_close",
  "sell_deadline": "t_plus_2_close",
  "hold_trading_days_max": 2,
  "do_not_buy_before_release": true,
  "chase_gap_pct_block": 15
}
```

### 3A.4 买入过滤（写入推送「风险」旁）

| 条件 | 动作 |
|------|------|
| 财报数字尚未发布 | **不买**（T-2 推送只是提醒准备） |
| 盘后/开盘相对前日收盘跳空 **≥ 15%** | `buy_ok=false`，标注不追 |
| 财报前 30 日涨幅 **> 25%** | 本就应硬淘汰；若仍展示则 `buy_ok=caution` |
| miss / 下调指引（人工或后续版本识别） | 不适用本策略，应回避 |

### 3A.5 与「提醒提前 2 天」的区别（避免混淆）

| 概念 | 含义 | 数值 |
|------|------|------|
| **推送提前量** | 手机何时提醒你「要发财报了」 | 财报前 **2 个自然日**（T-2） |
| **持有/受益窗口** | 数字落地后建议持有多久 | 发布后约 **2 个交易日**内卖完 |

两者都是「2」，但是 **推送日历** vs **交易持有**，文档与 UI 必须分开表述。

### 3A.6 实现位置

```
app/earnings_monitor/trade_window.py
  compute_trade_window(earnings_date, session) -> strategy, buy_window, sell_window, sell_deadline, buy_window_json
```

入库、列表 API、详情 API、网站表格、Push 正文 **全部调用同一函数**，禁止各写各的文案。

## 4. 系统架构（对齐 Athena）

```
app/
  earnings_monitor/
    __init__.py
    config.py              # 阈值（可 re-export app.config）
    universe.py            # 加载 earnings_universe.json + 市值过滤
    calendar_fetch.py      # 拉取下次财报日（Finnhub / Yahoo 等）
    scoring.py             # 实现评分规则六维 + 硬淘汰
    trade_window.py        # POST_ER_BUY_WITHIN_2D 买卖窗口计算
    pipeline.py            # 抓日历 → 打分 → 算窗口 → 入库 →（条件）推送
    push.py                # 合并推送文案（含买卖窗口）
  database.py              # 新增 EarningsEvent / EarningsPushBatch
  routes.py                # /api/earnings* 
  scheduler.py             # 日历刷新 + 每日 T-2 推送检查
  push_format.py           # build_earnings_push_content(...)
templates/
  deals.html               # 增加「财报日历」Tab + 表格（含买卖列）
data/
  earnings_universe.json
```

### 4.1 数据流

```
每日 / 每 N 小时
  → calendar_fetch：刷新 universe 内各 ticker 的 next_earnings
  → 写入/更新 EarningsEvent（状态 calendar）
  → compute_trade_window(session) → 写入 buy/sell 字段
  → 若 days_to ≤ 14：跑 scoring → 更新 score / eliminate_reason
  → 网站 API 立刻可读（含买卖窗口）

每日美东 09:00（可配置）
  → 选出 days_to == 2 且 score ≥ 75 且未成功推送的事件
  → 按 earnings_date 合并
  → 一条手机推送
  → 写 EarningsPushBatch + 回写各事件 pushed_at

若 T-2 失败
  → T-1 同一任务补推（ALLOW_T_MINUS_1）
```

### 4.2 调度建议

| Job | 触发 | 作用 |
|-----|------|------|
| `earnings_calendar_refresh` | 每 6 小时 或 美东 08:00 | 刷新财报日、市值、基础字段 |
| `earnings_score_refresh` | 美东 08:30（交易日） | 对未来 14 日候选重算分 |
| `earnings_t2_push` | 美东 **09:00** 每日 | 扫描 T-2（及补推）合并推送 |

不要把财报推送绑在 `deal_monitor` 的分钟级轮询里发手机；日历刷新可以共用或独立。

## 6. 评分引擎落地要点

完整规则见评分规则文档。工程侧注意：

1. **硬淘汰优先**：`eliminate_reason` 非空 → `push_eligible=false`，网站可灰显并显示淘汰原因。
2. **深度评分窗口**：仅对 `days_to ≤ 14`（交易日或自然日，建议自然日简化）跑六维；更远的只显示日期 + 「待评分」。
3. **网站 vs 推送**：
   - 网站：`WEB_MIN_SCORE` 默认 0（展示全部 upcoming）
   - 推送：`PUSH_MIN_SCORE` 默认 75
4. **唯一首选逻辑**：评分规则里的「只输出 1 家」用于 **AI 人工分析 / 可选高亮**；手机推送是 **所有 ≥75 且 T-2 的合并列表**，不强制只推 1 家。
5. 表格可增加列「本周首选」：对同一财报周跑决胜规则，给 Top1 打星（可选，v1 建议做）。

### 7.1 表格列（建议）

| 列 | 内容 |

| 时段 | 盘前 / 盘后 / 待定 |

移动端表格可折叠「买卖」为单列：`买：…｜首选卖：…｜最晚：…`。

### 7.2 默认筛选与排序

- 默认：`status=upcoming` 且 `earnings_date` 在未来 90 天
- 排序：`earnings_date ASC`，同日按 `score_total DESC`
- 筛选器：赛道、仅 ≥75、仅 T-2 窗口内、仅未推送

### 7.3 UI 文案提示（必须有）

> 手机推送仅在财报前 **2 天** 发送；更早的日程只在本页展示，避免打扰。同日多家合并为一条通知。  
> 买卖窗口：默认 **财报发布后尽早买，约 2 个交易日内卖完**（校准自 OKTA/CRWD/CRM）；**不是**财报前 2 天买入。跳空过大不追。非投资建议。

### 7.4 与合作快讯列表的区分

- 财报行 **不要** 混进合作事件流（类型不同）
- 可用 Tab：`合作快讯 | 黄仁勋 | 财报日历`
- 或同页上方固定「未来 14 日财报」折叠表，下方仍是事件流

### 8.1 标题

```
【小公司财报 T-2】{MM-DD} 共 {N} 家可关注
```

若仅 1 家：

```
【小公司财报 T-2】{TICKER} {MM-DD} {BMO|AMC} 得分 {score}
```

### 8.2 正文模板（HTML，与现有 push 风格一致）

```html

<b>说明</b>：非投资建议；beat 不代表必涨；跳空≥15%不追。<br>
<br>
<!-- 循环 -->
<b>{i}. {ticker}</b> {company} | 得分 <b>{score}</b>/100 | {session}<br>
理由：{one_liner}<br>
<b>买入</b>：{buy_window}<br>
<b>卖出首选</b>：{sell_window}<br>
<b>卖出最晚</b>：{sell_deadline}（2交易日内清仓）<br>
风险：{risk_oneliner}<br>
<br>
<!-- end -->
详情见网站：AI 产业链合作快讯 → 财报日历
```

### 8.3 不推送时的 channel 取值（对齐现有）

| channel | 含义 |
|---------|------|
| `too_early` | days_to > 2，仅网站 |
| `below_score` | 未达 PUSH_MIN_SCORE |
| `eliminated` | 硬淘汰 |
| `disabled` | 总开关关闭 |
| `rate_limited` | （财报合并推送一般不用按 ticker 限流；按 batch 去重即可） |
| `failed` / `unconfigured` | 与 deal_monitor 相同 |

远日事件 **不要** 写 `pushed_at`；可写 `push_channel=too_early` 便于调试，或保持 null + 网站用 `days_to` 计算状态。

## 13. 与对话结论对齐的产品说明（写给产品/运营）

1. **暴涨窗口**：OKTA/CRWD/CRM 类行情多从 **财报盘后** 启动，次日正规盘延续；最大受益约在发布后 **2 个交易日**内（策略 `POST_ER_BUY_WITHIN_2D`）。
2. **本模块 T-2 推送**：是 **发布前提醒**，不是叫你 T-2 就买入；买入应在 **数字落地后**。
3. **为何不更早推手机**：日历可提前数周发现，过早推送会造成疲劳，且分数会随预期/涨幅变化，T-2 重算更准。
4. **为何同日合并**：2026-08-26 三家同日财报；分三条推等于刷屏。
5. **两个「2」不要混**：推送提前 **2 自然日** ≠ 持有 **2 交易日**；UI 必须分开写清。
6. **评分文档关系**：本设计负责 **何时推、买卖窗口、怎么展示**；[评分规则](./小公司财报催化剂评分规则.md) 负责 **打多少分、谁能进推送池**。
